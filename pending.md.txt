Family Owner → Branches
Overall, the Branch module is well designed and mostly aligned with the client requirements. The structure correctly treats a branch as a lineage governance boundary, which matches the intended architecture of the platform.
Estimated alignment: ~75–80%
The following areas are working well, and a few areas may require refinement before final sign-off.
What Is Working Well1. Root Ancestor Linkage The branch configuration allows defining a Root Ancestor Node.
Example:
Root Ancestor: Charles Windsor


This is correct because the client specification defines that:
Branches are lineage groupings connected to a root ancestor within the unified clan tree.
This ensures branches are not separate trees, but structured segments of the main genealogy graph.
2. Branch Leadership
The screen allows defining a Branch Head.
Example:
Branch Head: Prince William


This aligns with the intended structure where each branch has a recognized lineage leader or representative.
This role can later support features such as:
branch moderation
branch invitations
branch event leadership


3. Invite Policy
The branch settings allow choosing between:
Open Invite
Admin Approval Required


This aligns with the client requirement for controlled onboarding and claim approval flows, especially when users attempt to join a branch.
4. Permission Overrides
The branch-level permission overrides are well implemented.
Examples include:
Who can add members
Who can edit branch history
Media upload privileges


These settings allow branches to define their own internal contribution rules, which aligns with the requirement for branch-scoped governance.
Areas That May Need Adjustment

1. Branch Admin Role
Currently the interface only shows:
Branch Head

These roles serve different purposes:
Role
Purpose

Branch Admin

In many families, the elder lineage head may not be the person managing the digital platform.
Recommendation:
Add a separate field:

The platform includes strong privacy requirements, so branches should support visibility modes such as:

Family Tree
1. Relationship Approval Workflow
The current UI suggests edits happen directly.
However, the client specification requires:
Relationship edits should be request-based.
Member submits change request.
Admin approves.
This prevents incorrect lineage edits.
Recommendation:
When a non-admin user edits relationships, the system should create:
Relationship Change Request
Status: Pending / Approved / Rejected
Admins approve in the moderation queue.
2. Claim System Integration
The tree does not visibly show whether a person is:
claimed by a user


unclaimed profile


managed by guardian (minor)


The client requirements include an Identity Claim System.
The UI should show something like:
✓ Claimed
Unclaimed
Guardian Managed
This is important because genealogy nodes may exist without accounts.
3. Branch Labels
The current nodes do not show branch affiliation.
But branches are a governance boundary in the platform.
Nodes should optionally display:
Branch: Windsor
Branch: Spencer
This helps admins understand lineage structure inside the tree.
4. Privacy Indicators
The client requirements include field-level privacy control.
Examples:
hidden birth date


private person


minor protection


Currently the UI shows all fields equally.
There should be indicators such as:
🔒 Private
👶 Minor
This prevents accidental exposure.
